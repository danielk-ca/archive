The short answer is no, this setup will not perform as well as if the hard drives were connected directly to the primary machine via SATA. While it is a functional and common "compute vs. storage" architecture used in enterprise data centers, the home-grade hardware and networking involved introduce specific bottlenecks.

Here is a breakdown of why this setup differs from direct-attached storage (DAS) and how it would realistically perform.

1. The Network Bottleneck

The most significant limitation is the "pipe" between the two machines.

  • Direct SATA: A SATA III connection provides a theoretical bandwidth of 600 MB/s. Even a standard mechanical hard drive can saturate 150–250 MB/s.

  • Ethernet (iSCSI): The Asustor AS3304T features a 2.5GbE port. If your primary machine also has a 2.5GbE port (and your switch supports it), your theoretical max is roughly 312 MB/s. If either side is limited to standard 1GbE, you are capped at roughly 113 MB/s.

In a direct-attached setup, if you have four drives in a RAID 0 or certain Unraid configurations, your throughput can scale. Over iSCSI, you are forever capped by the speed of the network cable, regardless of how many drives are in the Asustor.

2. Latency and Protocol Overhead

SATA is a "low-level" protocol with near-zero latency. iSCSI, however, wraps disk commands inside TCP/IP packets.

  • CPU Impact: The secondary machine’s CPU (the Realtek RTD1296) must process these network packets and translate them back into disk commands. While iSCSI is more efficient than SMB or NFS, an ARM-based CPU with 2GB of RAM will struggle with high IOPS (Input/Output Operations Per Second) compared to a native SATA controller on an Intel i7 system.

  • Seek Times: For large file transfers (like movies), you might not notice the latency. However, for "chatty" applications like databases, Plex metadata folders, or running Virtual Machines, the slight delay in every request (latency) will make the system feel significantly slower than local storage.

3. Unraid Compatibility and Management

Using Unraid as the "Primary" node with iSCSI storage creates a unique challenge:

  • Array Mechanics: Unraid’s primary strength is managing individual disks, calculating parity, and allowing for easy expansion. If you present storage via iSCSI, Unraid sees the entire Asustor volume as one single "Unassigned Device." * Parity Issues: You cannot easily use Unraid’s parity system on top of an iSCSI LUN without significant performance penalties, as every write would have to travel across the network twice (once for the data, once for the parity calculation).

  • Failure Points: If the Asustor reboots or the network blips, the iSCSI target drops. Unraid often handles "missing" disks poorly if they disappear while the array is started, potentially leading to "stale" mounts or crashed Docker containers.

The "Verdict"

This setup will work, but it will feel like a functional compromise rather than a performance boost.

When it makes sense:

  • If the primary machine has no physical room for more hard drives.

  • If you primarily use the storage for Media Streaming (Plex/Jellyfin). A 4K Remux rarely exceeds 125 Mbps, so even a 1GbE link is plenty for playback.

When it fails:

  • If you intend to run Apps/Docker/VMs off that storage. The latency will make the interface laggy.

  • If you are doing heavy file transfers or video editing, where you will constantly hit the 1GbE or 2.5GbE "ceiling."

Recommendation: Keep your "App Data" (Docker configs, databases, and metadata) on a local SSD/NVMe drive inside the Primary machine. Use the iSCSI/Asustor setup strictly for "cold" or "bulk" data like movies, photos, and backups.

How many drives are you planning to put into the secondary machine, and do you already have 2.5GbE networking gear in place?
